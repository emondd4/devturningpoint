## Why OpenTofu exists in the conversation

Teams that standardize on Terraform-compatible HCL may evaluate OpenTofu for licensing, governance, or community roadmap reasons. Awareness beats surprise mid-migration.

## Mental model

<Callout type="mental-model">
  OpenTofu aims to remain largely compatible with Terraform workflows: `.tf` configs, providers, state. Always verify version pin and provider constraints before switching CLIs.
</Callout>

```hcl
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
```

Treat state backends, lock files, and CI binary choice as explicit decisions—not defaults.

## Common mistakes

- **Assuming 100% drop-in forever** — Read release notes; test plan/apply in non-prod.
- **Mixing CLIs casually on one state** — Standardize tooling per environment.
- **Ignoring provider registry differences** — Confirm sources you actually use.

## Interview angle

<Callout type="interview">
  What would you validate before proposing OpenTofu for an existing Terraform AWS stack?
</Callout>

## Practice checklist

- [ ] Read OpenTofu intro docs and note compatibility claims.
- [ ] Run `plan` against a tiny module in a sandbox.
- [ ] Document CLI version pinning for CI.
