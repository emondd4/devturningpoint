## Why SSH hardening matters

SSH is the front door to servers. Default password logins, shared root keys, and open `PermitRootLogin` turn one stolen credential into a full outage—or worse.

## Mental model

<Callout type="mental-model">
  Authenticate with short-lived or strongly protected keys (or certificates), authorize the minimum user/group, and constrain what that session can do. Prefer bastion/jump hosts over exposing every box to the internet.
</Callout>

## How to harden (practical baseline)

```sshd_config
PasswordAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
AllowUsers deploy
ClientAliveInterval 300
MaxAuthTries 3
```

```bash
# Generate an ed25519 key for a human operator
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/dtp-prod -C "operator@dtp"
# Restrict a key (authorized_keys)
# command="/usr/local/bin/restricted-shell",no-port-forwarding,no-agent-forwarding ssh-ed25519 AAAA...
```

- Use a bastion: developers SSH to jump host, then to private subnets.
- Prefer `sudo` for elevation over logging in as root.
- Rotate keys when people leave; never commit private keys.

## Common mistakes

- **One shared deploy key forever** — No attribution, painful rotation.
- **Agent forwarding to untrusted hosts** — Key material can be abused.
- **Opening 22/tcp to 0.0.0.0/0 “temporarily”** — Temporary becomes permanent.

## Interview angle

<Callout type="interview">
  How would you lock down SSH for a small production fleet without locking your team out?
</Callout>

## Practice checklist

- [ ] Disable password auth on a lab VM and verify key login.
- [ ] Sketch a bastion + private app servers diagram.
- [ ] Document key rotation steps for one engineer leaving.
