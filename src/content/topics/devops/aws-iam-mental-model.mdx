## Why IAM is the real AWS “firewall”

Misconfigured IAM causes more lasting damage than open security groups: identity can call APIs across regions and accounts.

## Mental model

<Callout type="mental-model">
  Who (principal: user/role/service) + What (actions on resources) + When/Where (conditions) = allow/deny. Prefer roles assumed temporarily over long-lived access keys. Deny statements and SCPs can override allows.
</Callout>

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": ["arn:aws:s3:::topics-uploads/prod/*"],
      "Condition": {
        "StringEquals": { "aws:PrincipalTag/team": "platform" }
      }
    }
  ]
}
```

## Practical habits

- Humans: SSO → assume role; avoid IAM users with keys when possible.
- Workloads: instance/task roles; CI via OIDC.
- Start narrow `Action`/`Resource`, expand with evidence.

## Common mistakes

- **`Action: "*"` on `Resource: "*"` “just to unblock”** — Creates standing privilege.
- **Sharing access keys in chat** — Rotate immediately if it happened.
- **Confusing authentication with authorization** — Login ≠ permission to delete buckets.

## Interview angle

<Callout type="interview">
  How would you grant a NestJS ECS task read-only access to one S3 prefix?
</Callout>

## Practice checklist

- [ ] Read an IAM policy and rewrite it more narrowly.
- [ ] Prefer role assumption over static keys for one CI job.
- [ ] List principals that can modify production infra.
