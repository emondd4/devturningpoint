## Why “we have snapshots” is not a DR plan

Disk failure, ransomware, and bad migrations need tested restores with known RPO (how much data loss is tolerable) and RTO (how fast you must be back).

## Mental model

<Callout type="mental-model">
  Backup = durable copy. Restore test = proof. Replication ≠ backup (logical deletes replicate). Match strategy to RPO/RTO and data criticality.
</Callout>

```bash
# Conceptual Postgres logical backup (verify in staging)
pg_dump --format=custom --file=app.dump "$DATABASE_URL"
pg_restore --clean --if-exists --dbname="$RESTORE_URL" app.dump
```

Automate backups; alert on failure; periodically restore to a scratch environment.

## Common mistakes

- **Never testing restores** — Corrupt dumps surprise you during outages.
- **Same-account-only copies** — Account compromise can delete backups too.
- **Ignoring application consistency** — Quiesce or use DB-native backup tools.

## Interview angle

<Callout type="interview">
  Define RPO/RTO for a payments database and choose a backup approach.
</Callout>

## Practice checklist

- [ ] Measure current backup age and last restore test date.
- [ ] Document where backups live and who can restore.
- [ ] Run a restore drill in non-prod.
