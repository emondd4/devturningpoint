## Why bash scripts fail in production

Ad-hoc one-liners become ops glue. Unquoted variables, ignored exit codes, and missing `set -e` turn rare failures into silent corruption.

## Mental model

<Callout type="mental-model">
  A script is a program: fail fast on errors, quote expansions, prefer arrays/functions over copy-paste. Exit codes are the API between tools.
</Callout>

```bash
#!/usr/bin/env bash
set -euo pipefail

deploy() {
  local env="$1"
  echo "Deploying to ${env}"
  ./bin/migrate --env "${env}"
}

deploy "${1:?usage: deploy.sh <env>}"
```

Prefer `[[ ]]` tests, `"${var}"` quoting, and `trap` cleanup for temporary files.

## Common mistakes

- **Unquoted `$paths`** — Word-splitting and globbing break filenames with spaces.
- **Ignoring pipeline status** — Use `set -o pipefail`.
- **Hardcoding secrets** — Inject via env or a secrets manager.

## Interview angle

<Callout type="interview">
  What does `set -euo pipefail` change, and when would you intentionally disable `-e`?
</Callout>

## Practice checklist

- [ ] Rewrite a manual deploy checklist as a script with functions.
- [ ] Add usage/`:?` parameter checks.
- [ ] Log to stderr; keep stdout for machine-readable output.
