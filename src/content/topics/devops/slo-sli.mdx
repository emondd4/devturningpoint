## Why SLOs beat “five nines vibes”

Uptime without a user-facing definition creates pager noise. SLIs measure what users feel; SLOs set a target; error budgets decide when to slow feature work.

## Mental model

<Callout type="mental-model">
  SLI = quantitative measure (e.g. successful HTTP requests / total). SLO = internal target over a window (e.g. 99.9% over 30 days). Error budget = allowed failure remaining before reliability work takes priority. SLA = customer-facing contract—usually looser than the internal SLO and tied to credits/penalties.
</Callout>

```promql
# Example availability SLI ratio (conceptual)
sum(rate(http_requests_total{code!~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))
```

## Common mistakes

- **Alerting on every CPU blip** — Alert on SLO burn instead.
- **Internal-only SLIs** — Disk free ≠ checkout success.
- **Impossible 100% targets** — Guarantees permanent firefighting.

## Interview angle

<Callout type="interview">
  Propose an SLI/SLO pair for a login API and how you would use the error budget.
</Callout>

## Practice checklist

- [ ] Pick one user journey and define an SLI.
- [ ] Set a realistic SLO window for that journey.
- [ ] Sketch when error budget exhaustion pauses releases.
