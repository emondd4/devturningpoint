## Why Compose beats a pile of docker run flags

APIs need Postgres, Redis, and a worker. Encoding the stack in `compose.yaml` makes onboarding and CI service containers one command, not tribal knowledge.

## Mental model

<Callout type="mental-model">
  Compose declares the desired multi-container app: services, networks, volumes, configs, secrets. The CLI reconciles that file with running containers.
</Callout>

```yaml
# compose.yaml
services:
  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://app:app@db:5432/app
    depends_on:
      - db
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: app
      POSTGRES_USER: app
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

```bash
docker compose up -d --build
docker compose logs -f api
docker compose down
```

## Common mistakes

- **Binding DB ports publicly in shared Wi-Fi labs** — Prefer internal networks; expose only what you need.
- **Committing real secrets in compose** — Use `.env` (gitignored) or secret stores.
- **Treating Compose as production K8s** — Great for local/CI; orchestrators differ at scale.

## Interview angle

<Callout type="interview">
  How would you give an API service a DNS name to talk to Postgres without hardcoding host IPs?
</Callout>

## Practice checklist

- [ ] Compose an API + Postgres + Redis stack.
- [ ] Use named volumes for DB data.
- [ ] Validate with `docker compose config`.
