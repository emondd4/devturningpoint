## Why process supervisors matter

SSH-ing in and running `node app.js &` dies on logout, loses logs, and restarts unpredictably. systemd (or a container orchestrator) owns lifecycle.

## Mental model

<Callout type="mental-model">
  A unit declares desired state: ExecStart, User, Restart, After=. journald captures stdout/stderr. `systemctl` is the control plane for that machine.
</Callout>

```ini
# /etc/systemd/system/topics-api.service
[Unit]
Description=Topics API
After=network.target

[Service]
Type=simple
User=app
WorkingDirectory=/opt/topics-api
ExecStart=/usr/bin/node dist/main.js
Restart=on-failure
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now topics-api
journalctl -u topics-api -f
```

## Common mistakes

- **Running as root “for convenience”** — Drop privileges with `User=`.
- **Forgetting daemon-reload** — Unit edits are invisible until reload.
- **Restart=always without backoff awareness** — Crash loops hide root causes.

## Interview angle

<Callout type="interview">
  How do you debug a service that exits immediately after `systemctl start`?
</Callout>

## Practice checklist

- [ ] Write a unit for a small HTTP process.
- [ ] Use `journalctl -u` and `--since`.
- [ ] Explore `systemctl cat` and drop-in overrides.
