## Why multi-cloud literacy matters even if you standardize on AWS

Job posts, clients, and acquisitions mix clouds. You need conceptual maps—not memorized every SKU—so you can translate architecture.

## Mental model

<Callout type="mental-model">
  Think in capabilities: compute, object storage, managed DB, IAM, networking, messaging. AWS is the primary lens; Azure/GCP have close cousins with different names and packaging.
</Callout>

| Capability | AWS | Azure | GCP |
|---|---|---|---|
| Object storage | S3 | Blob Storage | Cloud Storage |
| VMs | EC2 | Virtual Machines | Compute Engine |
| Managed Postgres | RDS/Aurora | Azure Database for PostgreSQL | Cloud SQL |
| Serverless functions | Lambda | Functions | Cloud Functions |
| Kubernetes | EKS | AKS | GKE |

Prefer portable skills (containers, IaC, observability) over trivia contests.

## Common mistakes

- **Claiming clouds are identical** — IAM, networking, and billing differ deeply.
- **Multi-cloud for vanity** — Complexity tax; choose deliberately.
- **Ignoring data egress costs** — Architecture economics matter.

## Interview angle

<Callout type="interview">
  A client asks to move an S3+RDS app to GCP. What capability mapping and risks do you discuss first?
</Callout>

## Practice checklist

- [ ] Map your current AWS stack to Azure/GCP names.
- [ ] Note one IAM difference that would change design.
- [ ] Estimate where egress fees might appear.
