## Why least privilege exists

If a compromised app runs as root (or Administrator), an attacker inherits the machine. Permissions shrink the blast radius when—not if—something goes wrong.

## Mental model

<Callout type="mental-model">
  Identity (who) × object (what) × action (read/write/execute/admin) defines access. Grant the minimum set that still lets the job succeed.
</Callout>

## Everyday Unix picture

```bash
# Who am I?
id
# Change ownership / mode carefully
# chmod 640 secrets.env   # owner rw, group r, others none
# chown app:app /var/app/data
```

Containers often run as a non-root user for the same reason: limit damage from RCE.

## Application-level cousins

OS permissions are not your only gate:

- DB roles with limited grants
- Cloud IAM policies
- Kubernetes RBAC

Same idea: **narrow identity, narrow actions**.

## Common mistakes

- **Running everything as root “to make it work”** — hides real permission needs.
- **World-writable deploy dirs** — any local user can plant binaries.
- **Copying `.env` into public image layers** — secrets leak via image history.

## Interview angle

<Callout type="interview">
  Your Node service needs to read TLS certs and write logs. How would you structure users, groups, and file modes?
</Callout>

## Practice checklist

- [ ] Run a local tool as a non-privileged user and note what breaks.
- [ ] Audit one project directory with `ls -la`.
- [ ] List cloud/DB roles your last service used.
