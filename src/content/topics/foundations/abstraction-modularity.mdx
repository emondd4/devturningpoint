## Why abstraction is not “more classes”

Abstraction means **separating what from how**. Good modules let you change storage, HTTP clients, or UI without rewriting the business rules. Bad abstraction adds layers that all know each other’s secrets.

## Mental model

<Callout type="mental-model">
  Draw a boundary: one side depends on an interface (ports); the other side provides an implementation (adapters). Depend inward on stable ideas, not outward on frameworks.
</Callout>

```ts
// Port
interface PaymentGateway {
  charge(input: { orderId: string; amountMinor: number }): Promise<void>;
}

// Adapter
class StripeGateway implements PaymentGateway {
  async charge(input) {
    /* Stripe SDK details stay here */
  }
}
```

## Cohesion and coupling

- **High cohesion** — a module’s parts serve one purpose.
- **Low coupling** — modules communicate through narrow APIs.

If every change requires editing five unrelated folders, boundaries are wrong—or missing.

## Common mistakes

- **God modules** — `utils.ts` that imports the world.
- **Premature frameworks** — abstractions before the second use case.
- **Leaking ORM entities** into UI/API layers.

## Interview angle

<Callout type="interview">
  How would you structure a codebase so swapping Postgres for another DB touches the fewest files?
</Callout>

## Practice checklist

- [ ] Name three modules in a project and their single responsibilities.
- [ ] Find one leaky abstraction and propose a narrower interface.
- [ ] Split a “utils” dump into purpose-named files.
