## Why SemVer exists

Without shared meaning for version numbers, “upgrade” is gambling. Semantic Versioning defines when it is safe to expect compatibility.

## Mental model

<Callout type="mental-model">
  Given `MAJOR.MINOR.PATCH`: **MAJOR** breaks API compatibility, **MINOR** adds features compatibly, **PATCH** fixes bugs compatibly (for public API). Pre-1.0 versions are often unstable by convention.
</Callout>

## Ranges (npm / many ecosystems)

```text
^1.2.3  → >=1.2.3 <2.0.0
~1.2.3  → >=1.2.3 <1.3.0
1.2.3   → exact
```

```json
{
  "dependencies": {
    "left-pad": "^1.3.0"
  }
}
```

Always verify what *your* package manager’s caret means—Dart pub’s `^` follows similar ideas but read pub docs for edge cases.

## Common mistakes

- Bumping only PATCH while shipping a breaking rename
- Assuming 0.x means “safe to upgrade wildly”
- Ignoring changelogs because “SemVer promised safety”

## Interview angle

<Callout type="interview">
  Your library renames a public function. Which SemVer component do you bump and how do you communicate migration?
</Callout>
