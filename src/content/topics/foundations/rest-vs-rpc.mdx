## Why this choice shows up in every architecture review

Teams argue “REST vs GraphQL vs gRPC” when they really mean: **resource model vs procedure model**, human-debuggable HTTP vs typed binary streams, and how clients evolve.

## Mental model

<Callout type="mental-model">
  **REST-ish HTTP APIs** expose nouns (resources) with methods and representations. **RPC** exposes verbs (procedures) you call with arguments—gRPC is a popular modern RPC stack over HTTP/2 with schemas.
</Callout>

## Side-by-side

| | REST-style HTTP | RPC (e.g. gRPC) |
| --- | --- | --- |
| Shape | `/users/42` + GET/PATCH | `UserService.GetUser` |
| Payload | Often JSON | Often Protobuf |
| Caching | URL-friendly | Less natural |
| Browser/tooling | Excellent | Needs generated stubs |

```http
GET /users/42 HTTP/1.1
Accept: application/json
```

```text
rpc GetUser(GetUserRequest) returns (User);
```

Neither is “more senior.” Public partner APIs often prefer HTTP+JSON; internal high-QPS service meshes often prefer gRPC.

## Common mistakes

- Naming RPC endpoints as nouns then using only POST for everything
- Pretending every JSON API is “RESTful” without resource design
- Ignoring versioning and idempotency in both styles

## Interview angle

<Callout type="interview">
  When would you pick gRPC between two backend services but keep REST for a mobile app?
</Callout>
