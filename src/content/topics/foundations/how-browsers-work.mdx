## Why browser internals matter to every web developer

Slow pages, FOUC, and “why did my script not see the DOM?” are not framework bugs—they are **critical rendering path** realities.

## Mental model

<Callout type="mental-model">
  Network bytes → parse HTML into **DOM** → parse CSS into **CSSOM** → combine into a **render tree** → layout → paint → composite. JS can interrupt parsing and mutate trees after load.
</Callout>

## Sketch of the path

1. Resolve DNS, TCP/TLS, fetch HTML.
2. Tokenize HTML; build DOM (preload scanner may fetch CSS/JS early).
3. Build CSSOM from stylesheets.
4. Layout (geometry), paint (pixels), composite layers.
5. Event loop handles input, timers, and callbacks.

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <link rel="stylesheet" href="/app.css" />
    <script defer src="/app.js"></script>
  </head>
  <body>
    <h1>Dev Turning Point</h1>
  </body>
</html>
```

`defer`/`async` change when scripts run relative to parsing—choose deliberately.

## Common mistakes

- Giant synchronous scripts in `<head>` blocking first paint
- Assuming CSS never blocks rendering
- Measuring only “backend TTFB” while ignoring client parse/layout cost

## Interview angle

<Callout type="interview">
  Explain DOM vs CSSOM vs render tree and one concrete way to improve Largest Contentful Paint.
</Callout>
