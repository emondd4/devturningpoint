## Why error handling is product design

Unhandled errors become blank screens. Over-handled errors become silent data corruption. Good systems classify failures: **transient**, **user-correctable**, and **programmer bugs**.

## Mental model

<Callout type="mental-model">
  Errors are data about a failed contract. Decide at each boundary: propagate, translate, retry, or terminate. Never catch just to log-and-continue unless the operation is truly optional.
</Callout>

## Categories

| Kind | Example | Typical response |
| --- | --- | --- |
| Transient | network blip | retry with backoff + jitter |
| User input | invalid email | 400 + field message |
| Authz | wrong role | 403, no detail leak |
| Bug | null deref | 500 + alert + fix |

```ts
type Result<T, E = string> =
  | { ok: true; value: T }
  | { ok: false; error: E };

async function fetchUser(id: string): Promise<Result<User>> {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (res.status === 404) return { ok: false, error: 'not_found' };
    if (!res.ok) return { ok: false, error: 'upstream' };
    return { ok: true, value: await res.json() };
  } catch {
    return { ok: false, error: 'network' };
  }
}
```

## Boundaries that matter

- **API edge** — map internal exceptions to stable status codes (see HTTP semantics).
- **UI edge** — show recovery actions; never dump stack traces to end users.
- **Job/worker** — dead-letter poison messages; do not infinite-retry forever.

<Callout type="warning">
  Empty `catch` blocks and “return null on any error” are common sources of production mysteries. Prefer explicit error types.
</Callout>

## Common mistakes

- **Catching `Exception` / `any` too broadly** — hides programmer bugs.
- **Retrying non-idempotent writes** — duplicate charges or inserts.
- **Leaking internals** — SQL text or file paths in client responses.
