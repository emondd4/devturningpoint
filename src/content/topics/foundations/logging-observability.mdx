## Why printf debugging does not scale to production

You cannot attach a debugger to every user’s phone. Observability means asking new questions of running systems using **logs**, **metrics**, and **traces**.

## Mental model

<Callout type="mental-model">
  Logs narrate events; metrics aggregate health (latency, error rate); traces connect a request across services. Together they answer *what happened*, *how bad*, and *where*.
</Callout>

## Structured logging habit

```js
// Prefer structured fields over string soup
console.log(JSON.stringify({
  level: 'error',
  msg: 'payment_failed',
  orderId: 'ord_123',
  code: 'CARD_DECLINED',
}));
```

Include correlation IDs so one user action can be found across services.

## Starter metrics

- Request rate, error rate, latency percentiles (RED method)
- Saturation (CPU, queue depth) for capacity

OpenTelemetry provides vendor-neutral instrumentation concepts used widely in industry.

## Common mistakes

- Logging secrets (tokens, passwords, card data)
- Unbounded debug logs that cost more than the product
- Metrics without labels that distinguish endpoints

## Interview angle

<Callout type="interview">
  A spike in p99 latency hit one endpoint. How do you use metrics vs traces vs logs to find the culprit?
</Callout>
