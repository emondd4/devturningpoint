## Why DNS is on the critical path

Before TCP/TLS/HTTP to `api.example.com`, something must answer: “Which IP?” DNS failures present as timeouts, intermittent outages, or “works on my machine” after local hosts file tricks.

## Mental model

<Callout type="mental-model">
  DNS is a distributed hierarchical database. Stub resolvers ask recursive resolvers, which walk from root toward authoritative name servers, caching answers along the way (TTL-bound).
</Callout>

## Common record types

| Type | Role |
| --- | --- |
| A / AAAA | IPv4 / IPv6 address |
| CNAME | alias to another name |
| MX | mail routing |
| TXT | arbitrary text (SPF, verification) |
| NS | delegates a zone |

```bash
# Explore resolution (tooling varies by OS)
dig example.com A +short
# or: nslookup example.com
```

## Caching and TTL

Short TTLs make changes propagate faster but increase query load. Long TTLs make mistakes linger. Cutover plans must respect TTL, not just “I updated the panel.”

## Common mistakes

- **Blaming the app for a DNS cutover** — half of clients still cache old answers.
- **Single point of DNS config** — one typo removes a product from the internet.
- **Hard-coding IPs** — bypasses DNS but creates brittle deploys.

## Interview angle

<Callout type="interview">
  A deploy changed an A record but some users still hit the old server—what is the most likely cause?
</Callout>

## Practice checklist

- [ ] Resolve a domain and note TTL.
- [ ] Explain the difference between recursive and authoritative servers at a high level.
- [ ] Find where your staging hostname is defined.
