## Why structure choice is a product decision

The “right” structure is the one that matches **how you query and update** data under real constraints (memory, concurrency, API shape)—not the fanciest name on a flashcard.

## Mental model

<Callout type="mental-model">
  Arrays = seats in a row (index by position). Hash maps = labeled lockers (index by key). Trees = org charts (parent/child navigation). Graphs = city maps (many-to-many links).
</Callout>

## Arrays / lists

Strengths: ordered iteration, cache-friendly contiguous storage (in many runtimes), index access (O(1)).

Weaknesses: inserting/removing at the front can be (O(n)); searching unsorted data is (O(n)).

```js
const ids = [10, 20, 30];
ids.push(40); // amortised O(1) at end
ids.includes(20); // O(n)
```

## Hash maps / dictionaries

Strengths: average (O(1)) get/set by key.

Weaknesses: no inherent order (unless insertion-ordered like JS `Map`); poor for range queries; memory overhead.

```js
const sessions = new Map();
sessions.set('user:42', { exp: Date.now() + 3600_000 });
console.log(sessions.get('user:42'));
```

## Trees

Use when hierarchy matters: file systems, UI widget trees, DOM, org data, indexes (B-trees in databases).

```js
const nav = {
  title: 'Docs',
  children: [
    { title: 'Foundations', children: [] },
    { title: 'Frontend', children: [{ title: 'React', children: [] }] },
  ],
};
```

## Selection cheat sheet

| Need | Reach for | Typical access/search | Typical insert |
| --- | --- | --- | --- |
| Ordered collection, scan often | Array | O(1) by index, O(n) search | O(n) at front, amortised O(1) at end |
| Frequent lookup by id | Hash map | O(1) average, O(n) worst case | O(1) average |
| Hierarchy / nested docs | Tree (balanced) | O(log n) | O(log n) |
| FIFO jobs | Queue | O(1) at head/tail | O(1) |
| Undo stack | Stack | O(1) at top | O(1) |
| Unique membership tests | Set | O(1) average (hash-backed) | O(1) average |

<Callout type="info" title="Worst case vs average case">
  Hash map/set O(1) is an *average-case* figure that assumes a decent hash function and low collision rate—a pathological input (or a weak hash) can degrade it to O(n). See `FOUNDATIONS-ALGORITHMS-COMPLEXITY` for how to reason about average vs worst case.
</Callout>


## Common mistakes

- **Using arrays for hot key lookups** — Repeated `find` on large arrays becomes a latency bug; use a Map.
- **Over-normalizing in memory** — Deep trees of tiny objects can hurt locality; sometimes a flat table is faster.
- **Ignoring uniqueness needs** — Sets prevent duplicate work; arrays silently accumulate dupes.
