## Why the distinction saves careers

Calling everything “multithreading” leads to wrong fixes: spinning threads for network waits, or expecting one CPU core to magically finish CPU-bound work faster with async/await.

## Mental model

<Callout type="mental-model">
  **Concurrency** structures tasks so progress can interleave (often while waiting on I/O). **Parallelism** runs work at the same time on multiple cores. You can have concurrency without parallelism (single-threaded event loop).
</Callout>

## Examples

```js
// Concurrent I/O on one thread (event loop)
const [a, b] = await Promise.all([
  fetch('/users/1').then((r) => r.json()),
  fetch('/users/2').then((r) => r.json()),
]);
```

```dart
// Concurrent awaits; still one isolate unless you spawn more
final results = await Future.wait([
  loadProfile(),
  loadOrders(),
]);
```

CPU-heavy loops need real parallel workers (threads, processes, Dart isolates)—not more `await`.

## Common mistakes

- Believing async/await uses all CPU cores automatically
- Sharing mutable state across threads without synchronization
- Blocking the event loop / UI isolate with CPU work

## Interview angle

<Callout type="interview">
  Contrast concurrency and parallelism, then explain when you would use a thread pool vs an event loop.
</Callout>
