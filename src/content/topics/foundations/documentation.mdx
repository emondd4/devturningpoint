## Why docs are a product surface

Undocumented systems create bus factor risk and slow onboarding. Good docs reduce Slack archaeology. Bad docs lie—which is worse than none.

## Mental model

<Callout type="mental-model">
  Match doc type to job: README (start here), ADR (why we chose X), runbook (when prod breaks), API reference (exact contracts). Keep each short and dated.
</Callout>

## Minimum useful set

1. **How to run locally** — one path that works.
2. **Architecture sketch** — boxes and arrows, not 40 pages.
3. **Operational truths** — who owns pages, where logs live.
4. **Decision records** — context, options, decision, consequences.

```markdown
# ADR-001: Use Postgres for order storage
## Context
We need transactions and relational reporting.
## Decision
Postgres 16 on managed hosting.
## Consequences
Team must learn SQL migrations; Redis remains cache-only.
```

## Common mistakes

- **Documenting aspirations as current reality**
- **Duplicating code comments that rot** — prefer linking to source of truth
- **No owner / last-updated date**

## Interview angle

<Callout type="interview">
  What would you put in a runbook for a payment service outage in the first 15 minutes?
</Callout>

## Practice checklist

- [ ] Add a “How to run” section that a teammate can follow cold.
- [ ] Write one ADR for a past decision.
- [ ] Delete or fix one obsolete doc paragraph.
