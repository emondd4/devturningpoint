## Why leaks feel like “random slowness”

Garbage-collected languages free unreachable objects. A **leak** is usually an unintended reference keeping objects alive—caches without bounds, listeners never removed, closures capturing large graphs.

## Mental model

<Callout type="mental-model">
  Reachability beats intention: if anything still points at an object (event bus, static map, DOM node, Flutter State), the GC cannot reclaim it. Profile **retained size** over time, not a single snapshot.
</Callout>

## Typical leak patterns

```js
const cache = new Map(); // unbounded
function remember(user) {
  cache.set(user.id, user); // grows forever
}

window.addEventListener('resize', () => {
  // if this closes over a huge object and never removes, retention grows
});
```

In Flutter: controllers/subscriptions not disposed; `GlobalKey` misuse; giant lists held in long-lived notifiers.

## How to investigate

1. Reproduce with a loop (navigate open/close N times).
2. Take heap snapshots / memory charts before and after.
3. Find retaining paths; fix ownership (dispose, WeakMap, bounded LRU).

## Common mistakes

- Calling every OOM a “memory leak” (sometimes just large working set)
- Fixing symptoms with more RAM instead of ownership
- Ignoring native allocations outside the GC heap
