## What is this?

React updates the screen in three steps (official docs):

1. **Trigger** a render
2. **Render** components (call them to produce JSX)
3. **Commit** changes to the DOM

Browser **paint** happens after commit.

## Why the split matters

If you put side effects (network calls, subscriptions, DOM reads/writes) in the wrong phase, you get:

- duplicated requests in development Strict Mode
- flicker and race conditions
- “why did this run twice?” confusion

## Mental model

<Callout type="mental-model">
  Render = pure calculation of the next UI tree. Commit = apply the diff to the DOM. Paint = browser draws pixels.
</Callout>

## During render

React calls your component. On re-render it compares the new output to the previous one and **plans** DOM updates. It still should not mutate existing objects “on the side”.

## During commit

- Initial render: React creates DOM nodes and inserts them.
- Re-render: React applies the **minimal** DOM operations needed.

If the rendered output for a node is the same, React can leave that DOM node alone—so uncontrolled inputs can keep user-typed text across parent re-renders when the `input` element is reused.

## Debugging tip

When something “re-renders but the DOM looks unchanged”, that can be normal: render ran, commit decided no DOM surgery was required.

## Common mistakes

1. Fetching in render body (impure + can loop).
2. Measuring layout during render instead of after commit/effect.
3. Assuming every render paints.

## Interview angles

**Mid:** Explain trigger → render → commit.  
**Senior:** How would you locate a commit-phase layout thrash (forced reflow) in a large app?
