## Why this matters

Large apps need clear boundaries. ES modules give browsers and tools a standard way to load files once, share bindings, and analyze dependencies statically.

<Callout type="mental-model">
  Each module has its own scope. Named exports are live bindings; default export is one primary value. Circular imports often signal a design smell.
</Callout>

## ESM in practice

Prefer named exports for code you own. Remember that directives like `"use client"` also create module-graph boundaries in Next.js.

```ts
export type TopicId = string;

export function formatTopicId(id: TopicId): string {
  return id.toUpperCase();
}
```

## Common mistakes

- **Relying on global scripts** — Order-dependent and hard to tree-shake.
- **Default-export everything** — Harder refactors and worse autocomplete.
- **Ignoring circular deps** — Subtle undefined exports at runtime.

## Interview angle

<Callout type="interview">
  Explain the difference between a live named export binding and a copied CommonJS export.
</Callout>
