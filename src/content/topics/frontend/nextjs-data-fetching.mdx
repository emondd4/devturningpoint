## Why this matters

Wrong caching defaults mean stale dashboards or thundering herds to your API. Next.js couples `fetch` with a cache/revalidate model you must understand explicitly.

## Mental model

<Callout type="mental-model">
  Server fetch can be cached and revalidated by time or tag. Dynamic data needs `no-store` or on-demand revalidation. Client fetching still belongs for highly interactive, user-specific live data.
</Callout>

## How it works

Prefer server fetches for initial page data. Use `revalidate` / `revalidateTag` for ISR-like freshness. Use TanStack Query on the client when you need mutations, optimistic UI, and shared cache across navigations.

```ts
export async function getTopics() {
  const res = await fetch('https://api.example.com/topics', {
    next: { revalidate: 60, tags: ['topics'] },
  });
  if (!res.ok) throw new Error('Failed to load topics');
  return res.json();
}

// On mutation elsewhere:
// revalidateTag('topics');
```

## Common mistakes

- **Assuming all fetch is uncached** — Defaults may cache; read current Next docs for your version.
- **Client-only waterfall for SEO content** — Prefer server for primary content.
- **Caching personalized responses** — User-specific data must not be shared across users.

## Interview angle

<Callout type="interview">
  Explain revalidate (time-based) vs on-demand revalidation, and when you would still use a client-side query library.
</Callout>
