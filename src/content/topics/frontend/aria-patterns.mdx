## Why this matters

Custom widgets without correct roles and keyboard behavior exclude keyboard and screen-reader users—and fail audits. ARIA describes meaning when semantics are missing; it does not add behavior by itself.

## Mental model

<Callout type="mental-model">
  First rule of ARIA: do not use it if a native element works. If you must, match an Authoring Practices pattern: role + required attributes + keyboard model + focus management.
</Callout>

## How it works

Prefer `<button>`, `<dialog>`, native forms. For a custom disclosure or tabs, follow APG: `aria-expanded`, roving tabindex, and Escape/Arrow keys as specified.

```html
<!-- Prefer native dialog when possible -->
<dialog id="confirm" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Delete topic?</h2>
  <button type="button" id="cancel">Cancel</button>
  <button type="button" id="ok">Delete</button>
</dialog>

<!-- Custom disclosure: role + state -->
<button type="button" aria-expanded="false" aria-controls="panel">
  Details
</button>
<div id="panel" hidden>Hidden until expanded.</div>
```

## Common mistakes

- **aria-label on everything** — Often redundant or wrong; visible text is better.
- **Role without keyboard support** — role="button" on a div still needs Enter/Space and focus styles.
- **Announcing every UI change** — Live regions are for important updates, not noise.

## Interview angle

<Callout type="interview">
  When would you choose a native `dialog` element over a custom modal with role="dialog", and what focus rules must the custom version implement?
</Callout>

## Practice checklist

- [ ] Audit one custom widget against APG
- [ ] Fix a missing aria-expanded
- [ ] Test with keyboard only
