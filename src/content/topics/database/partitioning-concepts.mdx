## Why one giant table becomes operationally painful

Billions of rows slow vacuums, bloat indexes, and complicate retention deletes. Partitioning splits a logical table into physical children the planner can prune.

## Mental model

<Callout type="mental-model">
  Parent table + partitions by RANGE (time), LIST (tenant/region), or HASH. Queries with partition keys skip irrelevant children. Detach/drop old partitions for cheap retention.
</Callout>

```sql
CREATE TABLE measurements (
  measured_at timestamptz NOT NULL,
  device_id   text NOT NULL,
  reading     numeric NOT NULL
) PARTITION BY RANGE (measured_at);

CREATE TABLE measurements_2026_09
  PARTITION OF measurements
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

Partitioning is not a substitute for good indexes or query design.

## Common mistakes

- **Partitioning tiny tables** — Overhead without benefit.
- **Queries that omit the partition key** — Touch all children.
- **Too many partitions** — Planning and catalog bloat.

## Interview angle

<Callout type="interview">
  Would you partition an orders table by day or by customer_id—and why?
</Callout>
