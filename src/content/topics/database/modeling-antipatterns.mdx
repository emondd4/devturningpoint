## Why this matters

A schema that “works for the demo” can block indexing, integrity, and reporting six months later. Recognizing anti-patterns early is cheaper than multi-week migrations.

## Mental model

<Callout type="mental-model">
  Prefer explicit columns and constraints for data you query and enforce. JSON is a tool for flexible attributes—not a substitute for a model. Polymorphism and EAV need a clear query story.
</Callout>

## How it works

Add NOT NULL/FK/CHECK where invariants exist. Split hot JSON fields into columns when you filter on them. Avoid polymorphic FKs without enforcement strategy.

```sql
-- Anti-pattern: everything in JSON
-- CREATE TABLE entities (id uuid primary key, data jsonb);

-- Better: stable attributes as columns; flexible remainder in jsonb
CREATE TABLE topics (
  id text PRIMARY KEY,
  track text NOT NULL,
  difficulty text NOT NULL CHECK (difficulty IN ('beginner','intermediate','advanced')),
  metadata jsonb NOT NULL DEFAULT '{}'::jsonb
);

CREATE INDEX topics_track_idx ON topics (track);
```

## Common mistakes

- **EAV for core domains** — Queries become joins-of-joins; typing vanishes.
- **No foreign keys “for speed”** — Integrity bugs cost more than FK overhead.
- **Unbounded child tables without retention** — Growth kills vacuum and backups.
