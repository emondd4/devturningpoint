## Why “just add a lock” can create outages

Locks serialize conflicting writes. Hold them too long or in inconsistent order and you get queues, timeouts, and deadlocks under load.

## Mental model

<Callout type="mental-model">
  Postgres uses MVCC for readers; writers take row locks. `SELECT … FOR UPDATE` locks rows you intend to change. Deadlocks abort one waiter—applications must retry.
</Callout>

```sql
BEGIN;
SELECT id, stock
FROM products
WHERE id = 42
FOR UPDATE;

UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock >= 1;

COMMIT;
```

Keep transactions short; lock in a consistent table/row order; monitor `pg_locks` during incidents.

## Common mistakes

- **Locking entire tables casually** — Escalation hurts throughput.
- **Doing HTTP calls inside open transactions** — Holds locks forever.
- **Ignoring deadlock retries** — Random user-facing failures.
