## Why default isolation is a product decision

Checkout, inventory, and feed ranking behave differently under concurrency. Isolation levels trade anomaly prevention for throughput and lock contention.

## Mental model

<Callout type="mental-model">
  Phenomena: dirty read, nonrepeatable read, phantom. SQL defines levels; Postgres implements Read Committed (default) and Repeatable Read/Serializable with MVCC plus additional checks—not every textbook lock story.
</Callout>

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;
-- another session may commit changes; this snapshot stays stable
SELECT balance FROM accounts WHERE id = 1;
COMMIT;
```

Prefer application patterns (conditional updates, `SELECT … FOR UPDATE`) when Read Committed + careful writes suffice.

## Common mistakes

- **Assuming Read Committed prevents lost updates** — Two read-modify-write races still lose.
- **Serializable everywhere** — Aborts rise; must retry.
- **Long-lived Repeatable Read** — Snapshot bloat / conflicts.

## Interview angle

<Callout type="interview">
  Which isolation would you choose for seat reservation and how would you handle conflicts?
</Callout>

## Practice checklist

- [ ] Reproduce a nonrepeatable read under Read Committed.
- [ ] Try Repeatable Read and observe snapshot behavior.
- [ ] Document retry policy for serialization failures.
