## Why nested subqueries become unreadable

Business questions often need intermediate result sets: filter cohorts, then rank, then aggregate. CTEs name those steps; window functions compute across related rows without collapsing the grain.

## Mental model

<Callout type="mental-model">
  `WITH` defines named subqueries you can reference. Window functions (`OVER (...)`) look at a partition of rows while keeping each row. `PARTITION BY` is the group; `ORDER BY` inside the window defines peer ordering.
</Callout>

```sql
WITH recent_orders AS (
  SELECT id, user_id, total_cents, created_at
  FROM orders
  WHERE created_at >= CURRENT_DATE - INTERVAL '30 days'
)
SELECT
  user_id,
  total_cents,
  RANK() OVER (PARTITION BY user_id ORDER BY total_cents DESC) AS rank_in_user,
  SUM(total_cents) OVER (PARTITION BY user_id ORDER BY created_at) AS running_total
FROM recent_orders;
```

Use `ROW_NUMBER`, `RANK`, `SUM() OVER`, and frame clauses carefully—defaults matter.

## Common mistakes

- **Using windows when a simple GROUP BY suffices** — Extra complexity.
- **Forgetting PARTITION BY** — Global ranking when you meant per-user.
- **Recursive CTEs without a termination story** — Can loop pathologically.

## Interview angle

<Callout type="interview">
  Write SQL to show each user’s latest order without a correlated subquery—or explain a window approach.
</Callout>

## Practice checklist

- [ ] Rewrite a nested subquery using `WITH`.
- [ ] Compute a running total with `SUM() OVER`.
- [ ] Compare `RANK` vs `DENSE_RANK` on ties.
