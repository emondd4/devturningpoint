## Why more indexes are not more performance

Every index speeds some reads and slows writes. Anti-patterns create write amplification, unused indexes, and planners that still seq-scan.

## Mental model

<Callout type="mental-model">
  Index predicates the planner can match. Wrapping columns in functions, leading wildcards, or OR-tangled filters often defeats B-trees. Measure with EXPLAIN ANALYZE and `pg_stat_user_indexes`.
</Callout>

```sql
-- Anti-pattern: function on column prevents plain B-tree use
-- WHERE lower(email) = 'a@b.com'  without expression index

-- Better: expression index if needed
CREATE INDEX users_email_lower_idx ON users (lower(email));

-- Anti-pattern: low-selectivity boolean alone on huge tables
-- CREATE INDEX users_active_idx ON users (is_active);
```

Drop unused indexes; prefer composite indexes matching filter + sort order.

## Common mistakes

- **Indexing every foreign key blindly** — Sometimes useful, not always free.
- **Duplicate overlapping indexes** — Redundant maintenance.
- **Creating indexes CONCURRENTLY without monitoring** — Still consumes resources.

## Interview angle

<Callout type="interview">
  Name three indexing anti-patterns and how you would detect them in production.
</Callout>

## Practice checklist

- [ ] Find unused indexes via stats views.
- [ ] Fix one function-wrapped filter with an expression index.
- [ ] Remove a redundant index in a staging clone and compare write latency.
