## Why one primary becomes a single point of pain

Read scaling, regional latency, and failover planning push teams toward replicas. Understanding lag and consistency beats cargo-cult “just add read replicas.”

## Mental model

<Callout type="mental-model">
  A primary accepts writes; replicas apply changes asynchronously (or synchronously in stricter setups). Clients must tolerate lag or pin reads that need freshness to the primary. Replication copies corruption and deletes—backups remain mandatory.
</Callout>

```sql
-- On a primary (conceptual monitoring)
SELECT client_addr, state, sync_state, replay_lag
FROM pg_stat_replication;
```

Promote replicas carefully with fencing so two primaries never accept writes (split brain).

## Common mistakes

- **Reading your own write from a lagging replica** — Stale UX bugs.
- **Calling replicas “backups”** — Logical mistakes replicate.
- **No runbook for failover** — DNS/connection string chaos during outages.

## Interview angle

<Callout type="interview">
  Which queries can safely use async read replicas, and which must hit the primary?
</Callout>

## Practice checklist

- [ ] Diagram primary + 2 replicas for your app.
- [ ] Define lag SLO for replica reads.
- [ ] Separate backup strategy from replication.
