## Why jsonb exists without abandoning SQL

Product metadata, feature flags, and sparsely populated attributes change faster than migrations. `jsonb` stores queryable documents inside a relational row—with tradeoffs.

## Mental model

<Callout type="mental-model">
  Prefer `jsonb` over `json` for query/index support. Operators like `->`, `->>`, `@>` navigate and contain. GIN indexes accelerate containment; typed columns still win for hot filters.
</Callout>

```sql
CREATE TABLE events (
  id bigserial PRIMARY KEY,
  name text NOT NULL,
  payload jsonb NOT NULL
);

CREATE INDEX events_payload_gin ON events USING GIN (payload);

SELECT id
FROM events
WHERE payload @> '{"type":"signup"}'::jsonb;
```

Validate important fields in app or CHECK constraints; do not treat jsonb as a schemaless free-for-all forever.

## Common mistakes

- **Putting every column in jsonb** — Lose constraints and clear plans.
- **Indexing nothing then blaming Postgres** — Containment needs GIN or expression indexes.
- **Huge documents per row** — TOAST and update amplification hurt.

## Interview angle

</Callout>

## Practice checklist

- [ ] Insert and query with `@>` containment.
- [ ] Add a GIN index and EXPLAIN a filter.
- [ ] Extract a hot key into a generated/stored column.
