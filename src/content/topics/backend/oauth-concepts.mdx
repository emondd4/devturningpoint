## Why this matters

Users should not give your app their Google password. OAuth delegates authorization to an authorization server; OpenID Connect layers identity (authentication) on top.

<Callout type="mental-model">
  Know the roles and the authorization code flow with PKCE for public clients. Access tokens authorize API calls; ID tokens assert login (OIDC).
</Callout>

## Role map

Your API is often the resource server. Your SPA/mobile app is the client. Google/GitHub/Auth0 may be the authorization server.

```ts
export type OAuthRole =
  | 'resource-owner'
  | 'client'
  | 'authorization-server'
  | 'resource-server';

export const googleLoginRoles: Record<OAuthRole, string> = {
  'resource-owner': 'end user',
  client: 'Dev Turning Point web app',
  'authorization-server': 'Google',
  'resource-server': 'Google APIs / your API if validating tokens',
};
```

## Common mistakes

- **Using implicit flow for new apps** — Deprecated for SPAs; prefer auth code + PKCE.
- **Treating access tokens as proof of UI login only** — Know OIDC id_token vs access token.
- **Custom crypto instead of battle-tested libraries** — Easy to get redirects/state wrong.
