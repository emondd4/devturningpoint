## Why this matters

Multi-step writes (order + inventory + outbox) must succeed or fail together. Transactions prevent partial updates that corrupt business state.

<Callout type="mental-model">
  Open a transaction in the application/use-case service—not in every repository method. Keep transactions short; do not hold them across external HTTP calls.
</Callout>

## Service-level boundary

Pseudo-code shows the structure: begin → multiple writes → commit/rollback.

```ts
export async function enrollUser(
  db: {
    tx: <T>(fn: (trx: unknown) => Promise<T>) => Promise<T>;
  },
  input: { userId: string; courseId: string },
) {
  return db.tx(async (trx) => {
    await insertEnrollment(trx, input);
    await incrementSeatCount(trx, input.courseId);
    return { ok: true as const };
  });
}

declare function insertEnrollment(trx: unknown, input: { userId: string; courseId: string }): Promise<void>;
declare function incrementSeatCount(trx: unknown, courseId: string): Promise<void>;
```

## Common mistakes

- **HTTP calls inside transactions** — Long locks; amplified failures.
- **Transaction per tiny repo call** — No atomicity across steps.
- **Ignoring isolation needs** — Race conditions on seats/inventory.
