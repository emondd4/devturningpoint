## Why this matters

Authentication proves identity; authorization decides allowance. Guards give Nest a dedicated place for those decisions without cluttering controllers.

<Callout type="mental-model">
  Guards implement canActivate. They typically run after middleware and before pipes/interceptors. Prefer APP_GUARD registration when you need DI.
</Callout>

## Role guard sketch

Keep token parsing in auth middleware/strategy; keep permission checks in guards.

```ts
import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';

@Injectable()
export class AdminGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest<{ user?: { role?: string } }>();
    return req.user?.role === 'admin';
  }
}
```

## Common mistakes

- **Business rules inside guards** — Keep guards about access; put domain rules in services.
- **useGlobalGuards with `new`** — DI will not work—use APP_GUARD.
- **Confusing 401 vs 403** — Unauthenticated vs authenticated-but-forbidden.
