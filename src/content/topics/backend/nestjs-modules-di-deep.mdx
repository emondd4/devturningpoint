## Why this matters

Shallow “put everything in AppModule” apps become untestable and circular. Explicit module boundaries and DI scopes are how Nest stays maintainable at team scale.

## Mental model

<Callout type="mental-model">
  Modules declare and export providers. Importers see only exports. Default scope is singleton; request scope exists for per-request state but has cost. Prefer constructor injection over manual `new`.
</Callout>

## How it works

One domain module per bounded context. Export only what others need. Use custom providers for interfaces. Reach for `forwardRef` last—usually a boundary smell.

```ts
import { Injectable, Module, Scope } from '@nestjs/common';

export const TOPIC_REPO = Symbol('TOPIC_REPO');

@Injectable()
export class TopicsService {
  constructor(
    // interface-style token
    // @Inject(TOPIC_REPO) private readonly repo: TopicRepo,
  ) {}
}

@Module({
  providers: [
    TopicsService,
    { provide: TOPIC_REPO, useClass: PostgresTopicRepo },
  ],
  exports: [TopicsService],
})
export class TopicsModule {}

// Request-scoped example (use sparingly):
@Injectable({ scope: Scope.REQUEST })
export class RequestContext {
  userId?: string;
}
```

## Common mistakes

- **Circular module imports** — Extract a shared module or invert the dependency.
- **Request-scoping everything** — Performance and mental overhead; keep rare.
- **new Service() inside controllers** — Breaks DI and testing.

## Interview angle

<Callout type="interview">
  Explain singleton vs request scope in Nest, and how module exports control visibility of providers.
</Callout>

## Practice checklist

- [ ] Split a fat module
- [ ] Export only a service
- [ ] Inject via a custom token once
