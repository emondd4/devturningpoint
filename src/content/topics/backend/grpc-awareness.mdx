## Why this matters

Chatty internal JSON/HTTP can waste CPU and bandwidth. gRPC gives typed contracts, efficient binary payloads, and streaming—at the cost of browser and tooling complexity.

## Mental model

<Callout type="mental-model">
  Define services in `.proto`, generate stubs, speak HTTP/2. Great for internal microservice meshes. Public browser clients usually still want REST/JSON or gRPC-Web gateways.
</Callout>

## How it works

Use gRPC for internal high-QPS service boundaries. Keep public APIs REST/OpenAPI unless you control clients. Invest in contract versioning and load balancing awareness.

```protobuf
syntax = "proto3";
package topics.v1;

service Topics {
  rpc GetTopic (GetTopicRequest) returns (Topic);
  rpc ListTopics (ListTopicsRequest) returns (stream Topic);
}

message GetTopicRequest { string id = 1; }
message Topic { string id = 1; string title = 2; }
```

## Common mistakes

- **Forcing gRPC on browsers without a gateway** — Poor fit; prefer REST or gRPC-Web.
- **No deadline/timeouts** — Cascading latency across services.
- **Ignoring compatibility** — Proto field evolution rules matter.

## Interview angle

<Callout type="interview">
  Compare REST/JSON and gRPC for an internal payments service calling a ledger service 10k times/minute.
</Callout>
