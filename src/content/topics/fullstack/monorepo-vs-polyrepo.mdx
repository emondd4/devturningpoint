## Why the debate exists

Teams fight about repos because the choice shapes **ownership, CI times, versioning, and how safely you share code**.

## Mental model

<Callout type="mental-model">
  Monorepo: many projects, one git history—great for atomic cross-package changes. Polyrepo: one deployable per repo—clear ownership boundaries, independent release cadence, more versioning work at boundaries.
</Callout>

## Tradeoffs

| Concern | Monorepo | Polyrepo |
| --- | --- | --- |
| Cross-cutting change | One PR | Coordinated version bumps |
| CI | Needs path filters / affected builds | Naturally scoped |
| Access control | Harder (one repo) | Easier per team |
| Onboarding | One clone | Many clones + docs |

```yaml
# CI path filter idea (conceptual)
on:
  push:
    paths:
      - "apps/web/**"
      - "packages/ui/**"
```

## Common mistakes

- **Monorepo without affected builds** — Every PR rebuilds the world.
- **Polyrepo without API contracts** — Breaking changes surprise consumers.
- **Copy-paste “shared” folders** — Neither topology; just drift.

## Interview angle

<Callout type="interview">
  When would you split a fullstack NestJS + Next.js app into polyrepos vs keep a monorepo?
</Callout>

## Practice checklist

- [ ] List shared packages you would extract.
- [ ] Sketch CI affected-build rules for a monorepo.
- [ ] Document versioning for a shared UI kit in polyrepo land.
