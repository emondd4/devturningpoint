## Why notifications are a product feature

Password resets, invoice receipts, and “your order shipped” are not side effects you fire-and-forget from a request thread. They need **delivery guarantees, templates, and user preferences**.

## Mental model

<Callout type="mental-model">
  API records intent → queue/worker sends via provider → store delivery status → user preference center gates channels (email/push/SMS). Retries must be idempotent.
</Callout>

```ts
// Conceptual: enqueue, do not SMTP inside the HTTP handler
await bus.publish("notification.send", {
  type: "password_reset",
  userId,
  correlationId: req.id,
  idempotencyKey: `pwdreset:${userId}:${tokenHash}`,
});
```

## Practical rules

- Keep templates versioned; never hardcode critical copy only in code deploys if marketing edits often.
- Separate transactional vs marketing streams (unsubscribe rules differ).
- Log provider message IDs; never log raw tokens/OTP codes.

## Common mistakes

- **Sending email in the request path** — Latency and double-sends on retries.
- **No preference/unsubscribe story** — Compliance risk.
- **HTML-only bodies** — Accessibility and client quirks.

## Interview angle

<Callout type="interview">
  Design password-reset email delivery so refreshes and worker retries cannot spam the user.
</Callout>

## Practice checklist

- [ ] Sketch queue + worker for one transactional email.
- [ ] Define an idempotency key scheme.
- [ ] List preference toggles you would expose.
