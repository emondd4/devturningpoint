## Why QA needs SQL

UI and API assertions are incomplete without checking persistence: wrong totals, orphan rows, and silent partial writes.

## Mental model

<Callout type="mental-model">
  Arrange known seed data → exercise the feature → assert DB state with SELECT (and sometimes EXPLAIN for performance suspicions). Prefer read-only accounts in shared environments.
</Callout>

## Patterns

- Count and sum checks after transactions.
- Soft-delete vs hard-delete expectations.
- Idempotency: retrying a payment should not double-insert.
- Referential integrity after delete/cascade.

## Common mistakes

- **Writing to production for “checks”** — Use staging with backups.
- **Brittle absolute IDs** — Prefer unique markers you create.
- **Ignoring isolation** — Parallel tests colliding on shared rows.

## Interview angle

<Callout type="interview">
  After a refund API returns 200, what SQL checks prove money moved correctly?
</Callout>

## Practice checklist

- [ ] Write three validation queries for an order flow.
- [ ] Document a read-only QA DB role.
- [ ] Pair with a backend engineer on a data bug.
