## Why STLC matters

Testing is not a single activity at the end. STLC structures how you analyze, design, execute, and close quality work so risks are caught early.

## Mental model

<Callout type="mental-model">
  Typical phases: requirement analysis → test planning → test design → environment setup → execution → defect reporting → closure. In Scrum, compress these into each Sprint rather than a big waterfall gate.
</Callout>

## How it shows up in practice

- **Requirement analysis** — Clarify acceptance criteria and testability before coding freezes.
- **Planning** — Scope, risk priorities, entry/exit criteria, environments.
- **Design** — Cases, charters, data sets, automation candidates.
- **Execution & closure** — Trace results to risks; archive evidence for releases.

## Common mistakes

- **Waiting for “dev done”** — Late testing discovers expensive defects.
- **No exit criteria** — Releases ship on calendar pressure alone.
- **Ignoring environment readiness** — Flakes and false failures.

## Interview angle

<Callout type="interview">
  How would you apply STLC ideas inside a two-week Scrum sprint without waterfall gates?
</Callout>

## Practice checklist

- [ ] Map STLC phases to your team’s Definition of Done.

- [ ] List artifacts you keep after a release.
