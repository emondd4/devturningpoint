## Why “flutter build works” ≠ “store accepts it”

Local release builds can succeed while Play Console rejects unsigned ABBs or App Review rejects missing privacy disclosures. Deployment is **policy + crypto + packaging**.

## Mental model

<Callout type="mental-model">
  Android cares about package name, signing key continuity, and App Bundles. iOS cares about bundle id, provisioning profiles, certificates, and privacy nutrition labels. Losing a keystore can end an app’s update line.
</Callout>

## Android caveats

- Prefer **Android App Bundle** (`.aab`) for Play.
- Keep upload vs app signing keys straight; back up keystores offline.
- Permissions in `AndroidManifest` must match runtime requests and store declarations.

```bash
flutter build appbundle --release
```

## iOS caveats

- Certificates/profiles expire; CI needs secure access to signing assets.
- Privacy manifests / usage strings (`NSCameraUsageDescription`, etc.) must match features.
- Bitcode is historical; follow current Flutter iOS deploy docs for your SDK version.

## Common mistakes

- Debugging with a different bundle id than production
- Hardcoding staging API URLs into release flavors
- Ignoring 16 KB page size / target SDK requirements when Play raises the bar

## Interview angle
