## Why Untyped `List` and `Map` push bugs to runtime. Generics keep illegal states out of your APIs and improve AOT compiler feedback.

## Mental model

<Callout type="mental-model">
  A generic type is parameterized (e.g. `List<T>`). Dart generics are reified—you can often inspect type arguments at runtime. Bounds (`T extends Object`) restrict what callers may supply.
</Callout>

## How

### Collections and custom types

```dart
class Result<T> {
  const Result.ok(this.value) : error = null;
  const Result.err(this.error) : value = null;
  final T? value;
  final Object? error;
  bool get isOk => error == null;
}

T firstOrThrow<T>(List<T> items) {
  if (items.isEmpty) throw StateError('empty');
  return items.first;
}

final names = <String>['Nila', 'Rafi'];
final idToUser = <String, User>{};
```

## Common mistakes

- **Using `dynamic` to “save time”** — loses analysis.
- **Forgetting bounds** — nullable type params where you needed non-null.
- **Casting with `as` instead of modeling types**.

## Interview angle

<Callout type="interview">
  Explain reified generics in Dart and why `List<String>` is not just erased to `List` at runtime.
</Callout>

## Practice checklist

- [ ] Parameterize one helper with `<T>`.
- [ ] Add an `extends` bound on a custom generic class.
- [ ] Replace a `List<dynamic>` in your code.
