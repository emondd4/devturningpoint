## Why interviewers obsess over rebuilds

Flutter performance literacy is knowing that `build` is cheap compared to layout/paint—but unnecessary subtree rebuilds and layout thrash still jank lists. You must explain the three trees.

## Mental model

<Callout type="mental-model">
  Widgets are immutable configuration; Elements hold identity/State; RenderObjects perform layout and paint. setState marks an Element dirty; dependents of InheritedWidgets rebuild selectively.
</Callout>

## How

### Rebuild locality

```dart
class Counter extends StatefulWidget {
  const Counter({super.key});
  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int _n = 0;
  @override
  Widget build(BuildContext context) {
    // Only this State's subtree is scheduled from setState here
    return Column(
      children: [
        Text('$_n'),
        ElevatedButton(
          onPressed: () => setState(() => _n++),
          child: const Text('Inc'),
        ),
        const ExpensiveLeaf(), // const helps reuse Element when parent rebuilds
      ],
    );
  }
}

class ExpensiveLeaf extends StatelessWidget {
  const ExpensiveLeaf({super.key});
  @override
  Widget build(BuildContext context) => const Placeholder();
}
```

## Common mistakes

- **Equating “build called” with “painted everything”**
- **Putting InheritedWidget high with chatty updates**
- **Skipping keys in reorderable lists**

## Interview angle

<Callout type="interview">
  Walk through widget vs element vs render object, and how keys affect Element reuse.
</Callout>

## Practice checklist

- [ ] Explain a rebuild using Flutter DevTools rebuild profiler.
- [ ] Add const to a leaf widget and observe.
- [ ] Answer the three-trees question out loud once.
