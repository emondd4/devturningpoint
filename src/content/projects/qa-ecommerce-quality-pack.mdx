## Why this project matters

Before automation fame, strong manual/API design and bug communication make QA credible.

<Callout type="mental-model">
  Risk → coverage ideas → cases → evidence. Bugs need reproduce steps and expected vs actual.
</Callout>

## Skills this proves

Learning outcomes map to: QA-STLC, QA-TEST-DESIGN, QA-BUG-REPORTING, QA-API-TESTING, QA-MANUAL-TESTING.

## Prerequisites

Complete related topics first. If starting early, expect to backfill fundamentals under load.

## Architecture / approach

Pick a target store (open demo or self-built). Layers: strategy, functional cases, API checks, data validation.

Recommended tools: Test case sheet, Postman, Browser, SQL client, Any demo shop or local app.

## Step-by-step guidance

Work one milestone at a time. Restate the objective, implement the smallest vertical slice, run the validation checklist, then capture portfolio evidence before continuing.

1) Strategy. 2) Cases for browse→cart→checkout. 3) API pack. 4) SQL checks. 5) Bug reports.

## Validation checkpoints

Cases trace to risks; ≥3 high-quality bugs (or findings); API assertions pass on fixtures.

## Common errors

Vague cases; bugs without environment; only UI clicking without data checks.

## Debugging guidance

Narrow with logs/network; capture HAR; compare DB state.

<Callout type="tip" title="Hypothesis-driven debugging">
  One hypothesis → one falsifying check → update notes. Avoid blind retries.
</Callout>

## Tests / verification

This project produces tests—peer review cases for clarity.

## Security

Include authz/negative API cases; never attack systems you do not own.

## Performance

Light awareness checks only at this level.
