<Callout type="warning" title="Simulated vs real evidence">
  Practice artifacts are fine when labeled simulated. Never claim fabricated approvals, budgets, or outcomes as real results.
</Callout>

## Why this project matters

Multi-surface releases fail on dependencies and communication more than coding speed.

<Callout type="mental-model">
  Integration points first. Gates are explicit. Comms match audience. Rollback is planned.
</Callout>

## Skills this proves

Learning outcomes map to: PM-SCRUM, PM-STAKEHOLDERS, PM-RISK, PM-KANBAN, PM-JIRA.

## Prerequisites

Complete related topics first. If starting early, expect to backfill fundamentals under load.

## Architecture / approach

Simulated web+mobile+API feature. Produce release train plan, dependency map, QA gates, rollout, and status pack—label simulated.

Recommended tools: Jira/GitHub, Release checklist, Status report templates, RACI.

## Step-by-step guidance

Work one milestone at a time. Restate the objective, implement the smallest vertical slice, run the validation checklist, then capture portfolio evidence before continuing.

1) Feature framing. 2) Dependency map. 3) Release checklist/gates. 4) Comms plan. 5) Simulated status over 2 weeks.

## Validation checkpoints

Dependencies owned; gates binary/clear; rollback criteria written; status pack understandable.

## Common errors

Date-driven denial; no mobile store lag; stakeholder spam without decisions.

## Debugging guidance

If dates slip, re-sequence dependencies—don't only add meetings.

<Callout type="tip" title="Hypothesis-driven debugging">
  One hypothesis → one falsifying check → update notes. Avoid blind retries.
</Callout>
